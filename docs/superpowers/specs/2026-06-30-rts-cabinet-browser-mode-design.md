# Дизайн: RTS Cabinet Browser Mode

Дата: 2026-06-30

## Цель

Добавить режим сбора RTS-Tender из личного кабинета через отдельный постоянный профиль Google Chrome. Пользователь вручную входит в RTS через доступный ему способ авторизации, включая сертификат или ЭЦП. Парсер после этого использует уже открытую авторизованную сессию, читает видимые пользователю страницы закупок и передает найденные карточки в существующий pipeline: фильтрация, дедупликация, SQLite, Excel, JSON и HTML-отчет.

Режим не должен обходить CAPTCHA, платные API, технические блокировки или закрытые разделы без доступа. Если сессия истекла или сайт требует повторный вход, инструмент останавливается с понятным сообщением и просит пользователя перелогиниться вручную.

## Почему выбран Chrome-профиль

RTS отказал в API-доступе, но пользователь имеет легитимный доступ к личному кабинету. Самый практичный путь - не хранить пароль, сертификат или токены в коде, а сохранить авторизованную сессию в отдельном профиле Chrome:

- профиль изолирован от основного браузера пользователя;
- cookies и локальное состояние остаются на машине пользователя и не попадают в Git;
- пользователь сам проходит ЭЦП/сертификат, если площадка этого требует;
- автоматизация работает только с тем, что отображается в браузере после ручного входа.

## Пользовательский сценарий

1. Пользователь запускает `Открыть_RTS_кабинет_Chrome.bat`.
2. Скрипт открывает Google Chrome с отдельным профилем `browser_profiles/rts_chrome` и отладочным портом для локального подключения.
3. Пользователь вручную входит в RTS-Tender и открывает нужный раздел поиска закупок.
4. Пользователь запускает `Собрать_RTS_кабинет.bat`.
5. Парсер подключается к уже открытому Chrome, проверяет, что видна авторизованная страница, и применяет кабинетный сбор.
6. Если сессия активна, карточки попадают в общий отчет.
7. Если сессия неактивна, отчет не перезаписывается ошибочными пустыми данными; пользователь получает инструкцию повторить вход.

## Границы безопасности

Входит в область реализации:

- запуск отдельного Chrome-профиля;
- подключение к локальному Chrome через Playwright/CDP;
- ручной вход пользователя через интерфейс RTS;
- чтение видимых таблиц, карточек и пагинации;
- умеренные задержки между действиями;
- сохранение диагностического HTML/screenshot при ошибке для настройки селекторов.

Не входит в область реализации:

- автоматический ввод паролей, PIN-кодов, сертификатов или ЭЦП;
- обход CAPTCHA, антибот-страниц и rate-limit;
- скрытая имитация активности ради обхода правил площадки;
- скачивание закрытых документов, если пользователь явно не открыл их в интерфейсе;
- подача заявок или изменение данных в личном кабинете.

## Поддержание сессии

Базовая стратегия - не держать сессию искусственно вечной, а использовать постоянный профиль Chrome. Если RTS сохраняет авторизацию как Edge/Chrome обычно сохраняет web-сессии, следующий запуск продолжит работу без повторного входа.

Дополнительный `watch`-режим можно добавить только как мягкий монитор состояния:

- раз в 10-15 минут проверить заголовок текущей вкладки и наличие признаков страницы входа;
- не кликать по закупкам и не листать страницы без необходимости;
- при разлогине показать сообщение пользователю;
- не выполнять частые фоновые запросы.

Первый инкремент реализует сбор по команде. Watchdog оставляется вторым инкрементом после проверки реального поведения RTS.

## Архитектура

Новые элементы:

- `tender_parser/sources/rts_cabinet.py` - источник `RtsCabinetBrowserSource`, который подключается к Chrome и возвращает `TenderRecord`.
- `tender_parser/browser/rts_cabinet.py` - низкоуровневые функции Playwright: подключение к CDP, поиск активной вкладки RTS, чтение таблицы, переход по страницам.
- `tender_parser/browser/session.py` - проверка доступности Chrome debug endpoint и статуса сессии.
- `Запустить_RTS_кабинет_Chrome.bat` - открывает отдельный Chrome-профиль.
- `Собрать_RTS_кабинет.bat` - запускает parser-профиль кабинетного сбора.
- новый CLI-профиль `--profile rts-cabinet`, встроенный в текущий `argparse` рядом с `full`, `fast`, `local` и `rts`.
- документация `docs/RTS_CABINET_BROWSER_MODE.md`.

Профиль Chrome хранится в `browser_profiles/rts_chrome`. Папка `browser_profiles/` должна быть в `.gitignore`.

## Данные и нормализация

Минимальные поля из кабинетной выдачи:

- название закупки;
- ссылка на карточку;
- номер процедуры;
- заказчик;
- регион или место поставки, если есть в таблице или карточке;
- НМЦК/цена;
- дата публикации;
- срок подачи;
- статус;
- исходный текст строки или карточки.

Если поле отсутствует в таблице, источник не падает. Он сохраняет пустое значение и передает карточку в общий enrichment/filter pipeline. Для кабинетных данных `source` будет `rts-cabinet`, `detail_status` - `enriched`, `source_confidence` - выше публичного HTML-источника.

## Поиск и фильтры

Первый рабочий вариант не пытается полностью повторить все фильтры RTS из кода. Пользователь может вручную выставить:

- период, например последние 14 дней;
- статус актуальных процедур;
- региональные ограничения;
- ключевые слова или сохраненный фильтр RTS.

Парсер считывает текущую выдачу и прогоняет ее через наши существующие словари интересов:

- целевые регионы: Симферополь, Севастополь, Республика Крым, Крым, Запорожская область, Херсонская область;
- интересующие категории: компьютерная техника, МФУ, принтеры, расходники, климатическая техника, бытовая техника, канцелярия, электротехника, сейфы, стеллажи, шкафы, ящики;
- стоп-темы: ГСМ, топливо, дизель, капитальное строительство, ремонты зданий и дорог, лекарства и лекарственные препараты.

Второй инкремент может научиться сам вводить наши ключевые запросы в фильтры RTS, но только после фиксации реальных селекторов и поведения страницы.

## Ошибки и диагностика

Источник возвращает `SourceHealth`:

- `ok` - карточки собраны;
- `empty` - страница доступна, но карточек нет;
- `skipped` - Chrome не запущен;
- `blocked` - видна CAPTCHA, антибот-страница или явная блокировка;
- `error` - селекторы не нашли ожидаемую структуру;
- `partial` - часть страниц собрана, часть не прочиталась.

При `blocked` или странице входа источник не пытается продолжать. Диагностика сохраняется в `logs/rts_cabinet/`:

- URL активной страницы;
- короткий текст ошибки;
- screenshot;
- HTML текущей страницы, если это не страница с чувствительными персональными данными. Если есть риск чувствительных данных, HTML не сохраняется, только screenshot и URL.

## Тестирование

Тесты первого инкремента:

- unit-тест парсинга HTML-таблицы RTS cabinet fixture в `TenderRecord`;
- unit-тест распознавания страницы входа;
- unit-тест распознавания CAPTCHA/blocked;
- unit-тест, что `--profile rts-cabinet` добавляет кабинетный источник и не включает публичный RTS;
- тест launcher-файлов на наличие отдельного Chrome-профиля и правильного профиля запуска;
- smoke-тест CLI с fake/source fixture без реального Chrome.

Live-проверка с настоящим RTS выполняется вручную: открыть Chrome-профиль, войти в ЛК, открыть выдачу, запустить `Собрать_RTS_кабинет.bat`, проверить `exports/latest.html` и `exports/run_report.json`.

## Риски

- RTS может менять DOM-структуру кабинета; селекторы должны быть сосредоточены в одном модуле.
- Кабинет может требовать повторный вход чаще, чем ожидается; это нормальный operational сценарий.
- Запуск Chrome с отладочным портом небезопасен для общей сети; использовать только `127.0.0.1` и локальную машину.
- Если пользователь откроет не страницу выдачи, источник должен дать понятную ошибку, а не пустой отчет.
- Сертификаты и ЭЦП зависят от локальной установки CryptoPro/плагинов; парсер не управляет ими.

## Критерии готовности первого инкремента

- Есть кнопка для открытия отдельного RTS Chrome-профиля.
- Есть кнопка для сбора текущей RTS-выдачи из авторизованного Chrome.
- При активной сессии карточки попадают в общий Excel/JSON/HTML.
- При неактивной сессии пользователь получает понятную ошибку и отчет не затирается пустотой.
- В `run_report.json` виден источник `rts-cabinet` со статусом и количеством карточек.
- Полный `pytest` проходит.
